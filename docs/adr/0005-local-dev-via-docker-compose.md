# Local dev: full suite runnable via Docker

Postgres, the .NET API, and the Next.js app must all be runnable locally via Docker (a single `docker-compose.yml`), so any contributor can clone and run the whole stack with one command.

**Amended (2026-08-08) — nothing on the host but Docker.** The requirement is stronger than "runnable via Docker": the toolchain never touches the host machine. No .NET SDK, Node, npm, or EF tooling is installed locally — the host has Docker and an editor, and must not be assumed to have anything else. Every build, test, migration, package install, and codegen run executes inside a container (`docker compose run --rm <service> <command>`), and every documented workflow — README, scripts, CI — is written as a container invocation; a bare `dotnet` or `npm` anywhere is a bug. The editor experience comes from a Dev Container layered over the same compose stack, carrying both toolchains so IntelliSense and debugging resolve in-container. This applies to agents working on the repo exactly as it does to humans (see `CLAUDE.md`).

**Amended (2026-11-16) — no editor container (#151).** The Dev Container is removed, and with it the in-container IntelliSense and debugging the 2026-08-08 amendment describes. People edit on the host and run everything through compose from a host terminal; the dev overlay reloads on save. Agents work in the Docker Sandbox (`.sbx/`, `./sandbox.sh`), which carries the toolchain and the language servers. Keeping both meant pinning the same tools in two places, and two environments overwriting each other's restore output. Connecting VS Code to the sandbox over SSH was tried and works, but it is left out for now: everything in the sandbox runs as the agent's GitHub identity, and editing on the host with compose is enough for the owner. The build rule is unchanged: the host has Docker (plus `sbx` for agents), and every build, test, migration, package install and codegen run is a compose invocation.

**Amended (2026-11-17) — the sandbox's toolchain is a kit, not a template (#175).** sbx 0.51 made the built-in `claude` agent a v3 kit, and a sandbox can't combine v3 kits with v1 or v2 ones, so the v2 setup (a custom template image built and loaded by `sandbox.sh`, plus four v2 kits) could no longer create a sandbox. The kits are now v3, and the toolchain the template carried (the .NET SDK, Node and the two language servers) is a fifth kit's image content, which sbx builds itself. The rule doesn't change: the toolchain is still inside the sandbox, never on the host, and builds, tests, migrations and package installs are still compose invocations. The host needs sbx 0.51 or later.
