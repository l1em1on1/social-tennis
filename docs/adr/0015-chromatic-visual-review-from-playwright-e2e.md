# Visual review with Chromatic, captured from the Playwright E2E suite

ADR-0014 made Playwright the frontend test seam. It checks behaviour and accessibility, but nothing notices when a screen *looks* different: a token change, a broken layout, a badge in the wrong colour. We add Chromatic for visual review, and feed it from the suite we already have rather than a second set of tests.

- **Capture.** The E2E specs import `test` and `expect` from `@chromatic-com/playwright` instead of `@playwright/test`. Each test writes a DOM archive (DOM, styles, assets) of its final page to `web/test-results/chromatic-archives`, and `takeSnapshot` adds mid-test captures where a test passes through a screen worth reviewing (the `/dev/ui` showcase).
- **Mock project only.** Snapshots are taken in the `mock` project, whose data is fixed by the MSW handlers. The `real` project sets `disableAutoSnapshot`: its Users are unique per run and its data changes, so its snapshots would differ every build. For the same reason the mock project logs in as `player@example.com`, not a random `+tag` address. The real project also writes to its own `test-results/real`: the plugin keeps one `<test title>.stories.json` per test under `<outputDir>/chromatic-archives`, and with a shared directory the real project's empty lists overwrote the mock project's, so Chromatic received no snapshots.
- **Upload.** A `chromatic` compose service (profile `e2e`, same Playwright image, which has git) runs `npx chromatic --playwright` over the archives. It mounts the whole repo because the CLI reads git history to link builds to commits and find baselines. Like everything else, it runs in Docker (ADR-0005).
- **Gate.** CI runs it after a passing E2E run, with `--exit-zero-on-changes`: visual changes don't fail the job. Chromatic's own "UI Tests" status check on the PR holds the merge until a reviewer accepts or rejects the changes in Chromatic. The step is skipped while the `CHROMATIC_PROJECT_TOKEN` secret is unset, so the repo works without an account.

## Considered Options

- **Storybook + Chromatic.** Component-level stories, the canonical Chromatic setup, with modes for light and dark. Not rejected but deferred: it is a second toolchain, and the shell and screens are exercised by E2E already. It becomes worth it once the component set grows (Phase 1 screens), and is the planned way to snapshot dark mode.
- **Playwright's own `toHaveScreenshot`.** No service, but baseline PNGs live in the repo and must be regenerated in the exact same browser image; reviewing a diff means reading image files in a PR. Chromatic gives a review UI with per-change accept/reject and keeps baselines out of git.
- **Snapshot the real project too.** Rejected for now: nondeterministic data. Revisit if the real project gets seeded, fixed fixtures.

## Consequences

- Every E2E test in the mock project is also a visual test; adding a spec adds a snapshot. A spec that ends on a page not worth reviewing opts out with `test.use({ disableAutoSnapshot: true })`.
- Dark mode is not snapshotted: Chromatic documents colour-scheme modes for Storybook only, and a Playwright archive is replayed without the test's `emulateMedia`. The showcase spec therefore turns auto snapshots off and takes explicit ones in light mode only; dark contrast stays covered by axe.
- A `test.use({ disableAutoSnapshot })` inside a spec overrides the project-level setting, including the real project's opt-out. Set it to `true` there, never to a computed value that can be `false`.
- The e2e CI job checks out the PR's **head** commit with full history, not GitHub's merge commit, as Chromatic recommends for baselines. The E2E run therefore tests the branch as pushed, not the result of merging it.
- Visual changes need a reviewer in Chromatic, in addition to code review on GitHub.

**Amended (2026-11-16) — Dependabot PRs aren't visually reviewed (#158).** They see only Dependabot's own secrets, so Chromatic never runs on them, and the owner chose not to give them the token. A `web` job reports the required "UI Tests" status as passed on Dependabot PRs only, with the description "Not run on Dependabot PRs". Their other checks, the e2e suite included, still run. A dependency update that changes how pages look shows up in the next Chromatic build on `main`.

**Amended (2026-11-18) — component stories in Storybook (#46).** The deferred Storybook option is built, beside the E2E capture rather than instead of it. Every primitive in `components/ui`, the result-status badges and the bottom nav have stories, snapshotted in light and dark at 360px through Chromatic modes (`colorScheme`), which the Playwright archives can't do. Chromatic keeps Storybook and Playwright builds in separate projects, so the stories go to a second project linked to the same repo, with its own token (`CHROMATIC_STORYBOOK_PROJECT_TOKEN`). Once two projects are linked, Chromatic names each check after its project: the Playwright gate becomes "UI Tests: social-tennis", beside "UI Tests: social-tennis_storybook", so `main`'s required check and the Dependabot shim use those names. Storybook runs in a compose service like everything else. Components bound to a server action (the Player switcher, the Club, Player and League forms) have them too, with the actions mocked (#189). The `/dev/ui` showcase stays for its axe checks, and Manager pages get page snapshots separately (#187).

**Amended (2026-11-20): Manager and Admin pages from a fixed world (#187).** These pages had no snapshots. The specs that use them sign the Manager in on a second browser context, which the plugin doesn't archive, and they list whatever the parallel suite has added to the shared mock by then. So the mock now holds a small fixed world (`src/mocks/fixture.ts`): two Clubs, members in every state, Leagues, a League's requests and Players, and Users with each role. A session signed in as `snapshot-manager@example.com` or `snapshot-admin@example.com` reads that world, and so does any request for one of its ids. `e2e/manager-pages.spec.ts` signs in on the test's own page and ends on Manage, a League's Manager page and Admin, one test each. The fixed world brings its own dates. Playwright's `page.clock` couldn't have fixed them instead: the mock makes its dates on the server, and that clock only controls the browser.

- **Considered: Storybook stories of the pages.** Not chosen. Async server components render only behind Storybook's experimental RSC flag, the API client and the viewer would need mocks, and the shell would be missing. The issue also scoped this to the mock project.
- **Consequences.** A change to these pages shows in review only if the fixed world has the state it changes, so a new state goes into `fixture.ts`. The rest of the mock still stamps the real time; no other snapshot shows one of its dates yet.

**Amended (2026-11-20): the bottom nav on long snapshots (#182).** Chromatic captures the whole page, but draws a fixed element once, where it sits when the page loads. So on a page taller than the 780px screen, the bottom nav covered the content at the screen's bottom edge. Just before each capture, a page taller than the screen now gets the nav in normal flow, drawn once at its end. A page that fits keeps the nav pinned, as a phone shows it. `e2e/support/chromatic.ts` does this, and the specs import `test`, `expect` and `takeSnapshot` from it:

- an auto fixture that depends on the plugin's `chromaticSnapshot` fixture, so Playwright tears it down first, just before the automatic snapshot;
- a `takeSnapshot` wrapper, which puts the nav back after an explicit capture.

The override is a `<style>` with the page's CSP nonce (ADR-0027). The showcase no longer snapshots, because Storybook reviews every primitive in light and dark; its spec keeps the axe checks.

- **Considered:**
  - `cropToViewport`: everything below the fold would drop out of review.
  - Changing the shell: a sticky nav is frozen the same way, and a scrolling `main` makes Chromatic cut the snapshot at the screen's height.
- **Consequence:** this relies on `@chromatic-com/playwright` 1.0.0 taking the automatic snapshot as that fixture is torn down. If an upgrade changes that, the nav shows mid-page again, as a diff in Chromatic.

**Amended (2026-11-21): changes on `main` are accepted automatically.** PRs are squash-merged, so the commit on `main` isn't a descendant of the PR's commits. Chromatic should notice through GitHub and carry over the baselines accepted on the PR, but it didn't: every build on `main` reported "found 1 parent build", that is, the previous `main` build, and listed every snapshot as a change (98 of 98 stories, 37 of 38 tests). Nothing on `main` was ever accepted, so each PR was compared against nothing, and accepting on one PR didn't help the next. Both uploads now pass `--auto-accept-changes main`, as Chromatic's docs advise for this case: whatever lands on `main` becomes the baseline. Every change is still reviewed and accepted on its PR before the merge, and `main` only takes what was merged. Two runs of the suite gave the same visible text in all 42 Playwright snapshots, and none shows the day's date. The only differences were names in the partner picker's hidden list, from tests running in parallel, so nothing else makes a PR show changes it didn't make.
